### 3.2 「更新地址」和「下载地址」是两件事

| | 面向 | 形式 | 用途 |

1. **owner/repo 要改成真实的**：`huang957201826-cyber/panpan-workbench`（除非公开时决定改名，见 §7 Q4）。
2. **签名私钥绝不能进公开仓库**：现有 updater 私钥备份在 `E:\02-RUANJIAN\67-生图工作台-backups\updater-key\`。若走 CI 自动发布，必须放 GitHub Actions Secret；干净快照里不能有 `.env`、密钥、密码文件。

## 4. 第四条：依赖漏洞是什么意思？「建议升级，不要有安全漏洞」

**用户决定（已确认方向）**：升级，不接受带着安全漏洞开源。**升级范围与「零漏洞」口径仍待拍板（见 §7 Q2）**。

### 4.1 用大白话解释

- 软件不是从零写的，会引用几百个第三方代码包（React、Vite、Markdown 渲染、ZIP 压缩……）。这些包的作者后来发现自己代码有缺陷，会公开一条编号（GHSA / CVE）说明「哪个版本到哪个版本有问题、会造成什么后果、修在哪个版本」。
- `npm audit` 就是拿**本机锁文件里装的版本**去比对这份公开清单，报出「你装的这个版本命中了已知缺陷」。它不等于「你的软件已经被攻破」，而是「你明知道有补丁没打」。
- 严重度：critical > high > moderate > low；「直接依赖」是你自己写进 package.json 的，「传递依赖」是别人带进来的（比如 `streamdown → mermaid → dompurify`）；「开发依赖」只参与构建/测试，**不进安装包**，但开源仓库的自动扫描（Dependabot）照样会报。

### 4.2 本机实测（`npm audit --json`，2026-11-08）

| 范围 | 合计 | critical | high | moderate | low |
|---|---|---|---|---|---|
| 全量 | **23** | 1 | 9 | 6 | 7 |
| 仅生产（`--omit=dev`） | **7** | 1 | 0 | 1 | 5 |

生产侧 7 条：`dompurify`（critical）、`mermaid`（moderate）、`katex` / `@streamdown/math` / `micromark-extension-math` / `rehype-katex` / `remark-math`（low）。

**最要紧的一条**：`dompurify@3.4.7`（当前 `package.json` 的 `overrides` 写死 `^3.4.7`，`npm ls` 实测解析到 3.4.7）。它是给 Markdown/HTML 做「消毒」的库，命中 9 条 XSS / 净化绕过的公告（影响 `<=3.4.16`，修在 `>=3.4.17`）。`GO-LIVE-ASSESSMENT-20261107.md` 早就写了「`overrides` 改 `^3.4.17`，1 行修复」，但**至今没落地**。开源第一天任何扫描器都会把它标红，这是真正的发布阻断项。

### 4.3 「零漏洞」今天能不能做到？——必须说清楚

- **能清掉的**：critical 1 条（`dompurify` → `^3.4.17`）、moderate 1 条（`mermaid` 升到 audit 认可的修复版）、以及 dev 侧 16 条里绝大多数（`vite` / `postcss` / `undici` / `ws` / `nanoid` / `browserslist` / `vitest` / `wrangler` 等，`fixAvailable: true`）。
- **今天清不掉的**：`katex` 的公告范围 `>=0.11.0 <0.18.2`，当前 `^0.16.47`，`fixAvailable: false`；`@streamdown/math` 同样 `false`。原因是 `streamdown@2.5.0` 这套 Markdown 渲染链把 katex 版本锁住了，上游还没发出兼容的修复版。其余 4 条 low 都是它的下游传递告警。
- 也就是说，**只靠 `npm audit fix` 无法字面归零**。三条路：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（建议）** | 升级所有能升的，清到 **0 critical / 0 high / 0 moderate**，剩余低危上游未修项写进 README「已知限制」并注明公告编号与原因 | 诚实、不牺牲功能；但字面不是 0 |
| B | 为追求字面 0，替换/移除 `streamdown` 的数学公式与 mermaid 渲染链路 | 要动 Markdown 渲染功能，回归面大，且是「为了数字好看砍功能」 |
| C | 等上游发 katex 0.18.2 / streamdown 新版再发 | 发布时间不可控 |

- **dev 侧 16 条**：不进安装包，对本机用户零风险；但仓库一旦公开， Dependabot / `npm audit` 会把它们全列出来。既然用户要求「不要有安全漏洞」，我建议**一并升级**，但要单独作为一个批次处理：`vite 6.3 → ≥6.4.4（或 7.x）`、`vitest 4.1.5 → ≥4.1.12`、`wrangler 4.96 → >4.119` 等可能涉及大版本/跨版本升级，可能改配置或 API，必须 `tsc + 全量单测 + vite build + 实机` 全绿才算完成，不能和 UI-37 混在一次改动里。

> 我的建议：**方案 A + dev 依赖单独升级批次**。把「无 critical/high/moderate」写死为发布闸门；低危上游未修项如实登记，不隐瞒也不砍功能。若用户坚持字面 0，再切到方案 B 单独评估。

## 5. 第五条：K3「技能进 ZIP 备份」到底是什么意思（展开）

**本条用户只问「什么意思」**，下面是完整解释与取舍；是否做、何时做仍待拍板（见 §7 Q5）。

### 5.1 两个东西分别是什么

- **技能库**：P4 刚重做的「配方陈列馆」。你在输入台点「存为技能」，或在任务节点上保存，就生成一条配方（标题、提示词、分类、标签、封面、变量、负向提示词、收藏/置顶/使用次数等）。数据由 zustand persist 存在浏览器本地存储 `localStorage['panpan-prompt-skills-v1']`（`src/lib/skillStore.ts:68`）。
- **ZIP 备份**：设置里的「导出 / 导入」，以及删除任务/画布/项目前自动生成的「删除快照」。它打包 `manifest.json` + 图片文件，当前 `version: 4` 的 manifest 只含：`settings`、`tasks`、`agentConversations`、`favoriteCollections`、`defaultFavoriteCollectionId`、`workspace`、`imageFiles`、`thumbnailFiles`（`src/lib/exportZip.ts:132-153`），并且会 `scrubApiKeys` 把密钥抹掉。

### 5.2 「不进 ZIP」会怎样

`manifest` 里**没有 skills 字段**。后果：

- 换电脑、重装系统、清 WebView2 用户数据、卸载时删数据 → 任务、图片、项目都能从 ZIP 恢复，**只有自己攒的技能全没了**；
- 「删除快照 / 恢复」同样不带技能；
- 技能库是 P4 刚做成的核心功能，用户投入越多丢得越疼；
- 现在 `AUDIT-FINAL.md:70`、`GATES-FINAL.json`、`PLAN-FINALIZE.md`、`README` 都把它登记成「V1 已知边界」，即**故意没做，不是 bug**。

### 5.3 为什么当初没做（真实成本）

1. 技能在 `localStorage`，导出链路走的是 SQLite/图片文件体系，两套存储要打通；
2. 导入要有冲突策略：同 ID 覆盖还是跳过？内置技能与自建技能怎么区分？`usageCount` / `favorite` / 置顶要不要一起带？
3. 封面 `coverImageId` 指向图片，导出时要把关联图片一起打进 ZIP，否则恢复出来是空封面；
4. 提示词里可能带用户自己贴的敏感信息，导出前要复用 `scrubApiKeys` 的口径做清洗；
5. manifest 已 `version: 4`，加字段要考虑旧 ZIP 兼容与不变量测试（之前把「收藏」写进持久化就破坏过 10 条测试，教训还在）。

### 5.4 三个选项

| 方案 | 内容 | 评价 |
|---|---|---|
| **A（倾向）** | manifest 加可选 `skills` 字段，导出带上（含封面图），导入按「同 ID 覆盖 / 新 ID 追加」合并；补单测与 U2 导出→空库导入→技能数一致 | 一次性解决，用户体验最完整；改动覆盖导出/导入/删除快照，需小批次单独做 |
| B | 技能库里加「导出技能 JSON / 导入技能 JSON」两个按钮，不动 ZIP 结构 | 改动最小、风险最低；但用户要记得手动多导一次 |
| C | 维持现状，README「已知限制」写清「技能库不进备份」 | 零成本；开源后大概率被提 issue |

> 我倾向 **A**：既然这是「全部改完再开源」，K3 是唯一还挂着的 V1 已知边界，留到 1.1 会让 1.0.0 带着一个明显缺口发布。但若用户在意发布时间，B 是很好的折中。

## 6. 第六条：字体建议——国内软件一般用什么？

**用户问题**：建议改成什么字体？常规国内软件一般用什么字体？**仍待拍板（见 §7 Q1）**。

### 6.1 现状与约束（别推翻）

- UI 默认 `HarmonyOS Sans SC`，3 个 TTF 约 23.6 MiB；**其许可第 2 条明确禁止修改字体**，所以转 woff2 / 子集化 / 改 name 表都不允许（`UI-GAP-MATRIX §11.2`）。P5 已经合规地只瘦了 OFL 授权的等宽字体。
- 安装包 23.68 MiB 里，字体是大头。是否换 OFL 中文字体，本质是「**省约 20 MiB + 开源仓库更干净**」与「**观感变不变**」的交换。

### 6.2 国内软件的实际做法

**绝大多数国内桌面/网页软件不自带中文字体**，直接用系统字体栈，靠 CSS 回退：

```
"PingFang SC", "Microsoft YaHei", "Microsoft YaHei UI", "Noto Sans CJK SC", sans-serif
```

- Windows → 微软雅黑 / 等线；macOS → 苹方；Linux → Noto Sans CJK。用户看到的就是本机系统字形，安装包里一个中文字体文件都不放，也没有字体授权/再分发问题。这是微信、企业微信、飞书、钉钉、各类 Electron/Tauri 工具和后台系统最常见的做法。
- 注意：**「引用系统已装字体」和「把字体文件打包分发」是两回事**。微软雅黑不能打包进公开仓库（版权在方正，Windows 授权只覆盖系统使用），但写进 font-family 回退链完全没问题。
- 少数追求跨端一致观感的产品才会自带字体，且基本会选可自由修改的开源字体。

### 6.3 常见「免费商用」字体的授权差别（这轮专门核实过）

| 字体 | 授权性质 | 能否子集化 / 转 woff2 / 改文件 | 适合我们吗 |
|---|---|---|---|
| **思源黑体 / Noto Sans SC** | **SIL OFL 1.1**（真开源） | ✅ 允许修改、子集化、嵌入、随软件再分发；需保留 OFL 全文与版权声明，衍生版要改名（RFN） | ✅ **唯一能同时解决「瘦身 + 开源合规」的方案** |
| HarmonyOS Sans SC（现状） | 华为免费商用声明 | ❌ 许可禁止修改 | ⚠️ 可用，但瘦不了 |
| MiSans（小米） | 厂商许可协议，**不是 OFL** | ❌ 协议要求「软件中特别注明使用 MiSans」，且**禁止改编/二次开发、禁止单独再分发字体文件** | ❌ 和鸿蒙同样卡住子集化，还多一条署名义务 |
| 阿里巴巴普惠体 / OPPO Sans | 厂商免费商用声明 | ❌ 同为声明式授权，普遍禁止改编/二次分发 | ❌ 不适合瘦身 |
| 微软雅黑 / 苹方 | 系统字体，非可再分发字体 | 只可引用，不可打包 | ✅ 用于回退链 |

> 结论：**「换 OFL 中文字体」实际只有思源黑体 / Noto Sans SC 这一条路**，MiSans 之类的「免费商用」并不等于「可修改、可子集化」。

### 6.4 三个方案与我的建议

| 方案 | 做法 | 体积 | 观感 | 风险 |
|---|---|---|---|---|
| **A 不动** | 继续用 HarmonyOS Sans SC，3 个 TTF 原样 | 约 23.6 MiB | 和现在一模一样 | 零；但开源仓库里带一套「不可修改」的字体，法务观感略别扭，且永远瘦不下来 |
| **B 系统字体栈** | 删掉内置中文字体，`--font-ui-sans` 改 `"PingFang SC","Microsoft YaHei",...` | 再省约 20 MiB | 最「国内常规」，但 Windows 上字形会变（雅黑比鸿蒙略窄/旧），字重层级要复检 | 低；要全站截图 A/B，960 窄窗与 DPI 复检 |
| **C Noto Sans SC 子集** | 换成 OFL 的思源黑体，按现有 `scripts/build-font-subset.py` 思路子集化 + woff2，族名改衍生名，补 OFL 全文与版权、更新 `fonts.ts` / `index.css` / 设置页文案 / 第三方许可清单 | 约 1–3 MiB | 中性黑体，最接近「专业 UI 字体」，与鸿蒙有差异但不大 | 中；许可清单与设置页文案要同步，必须做 A/B 截图让你确认 |

**我的建议（首选 C，保守选 A）**：

- 如果目标是「**要开源 + 要瘦身 + 观感别大变**」，选 **C**：它是唯一把许可、体积、一致性一起解决的方案，且我们已经有 OFL 子集化的脚本与流程（Maple Mono 那次跑通了），不是从零开始。执行前先出一张「现状 vs 思源黑体」的同屏 A/B 截图，你点头再换。
- 如果不想再动观感、也不在乎 23.68 MiB（其实对桌面软件不算大），**A 完全可接受**，不要为了省体积制造视觉回归；把 HarmonyOS 的许可原文与「未修改副本」说明放齐即可。
- **B** 最贴近「国内常规」，但它是三者里观感变化最不可控的（取决于用户系统），我不作为首选。

## 7. 本轮新发现的 UI 缺陷：UI-37 浮岛下拉字号失控（需修，未修）

### 7.1 用户反馈

> 「点击输入框下面的所有按钮，字体都会变得很大。我觉得这个 UI 字体大小不合理。」

截图里「更多」弹出的「通道与元数据设置」面板，标题与左侧标签明显比底部胶囊大一圈。

### 7.2 实测证据（Playwright-core + Edge，1440×900，本地 dev server，只读验证）

切到**浮岛输入栏**后逐个点开 5 个胶囊：

| 对象 | computed fontSize | 备注 |
|---|---|---|
| `html` / `body` | **16px** | 全局没设根字号，Tailwind preflight 不设 font-size |
| `.studio-root` | 14px | `studio.css` → `var(--type-body)` |
| 5 个胶囊按钮（模型 / 尺寸 / 质量 / 数量 / 更多） | **12px** | `text-caption` |
| 弹出菜单容器 `[role="menu"]` | **16px** | `parent = BODY`（portal 挂到 `document.body`） |
| 模型 / 尺寸 / 质量 / 数量 菜单里的选项文字 | **16px** | 这些 `<div>/<span>` 没有字号类 |
| 「更多」面板标题 + 4 行标签（导出格式 / 透明背景通道 / 内容审核 / 批量提交） | **16px** | 只有颜色类 `text-slate-500`，无字号类 |
| 同一面板内的值按钮（PNG / WebP / 关闭 / auto…） | **12px** | 显式 `text-caption` |
| 「更多尺寸 / 比例…」 | 12px | 显式 `text-caption` |

→ 用户说的「所有按钮点开字体都变大」成立，且**同一个面板里 16px 与 12px 混排**，比单纯「偏大」更别扭。停靠模式（右侧工作台）的对应菜单是另一套实现，之前实测为 12px，不受影响。

### 7.3 根因

1. `src/ui/Menu.tsx:153-166` 用 `createPortal(..., document.body)` 把菜单挂到 `body`；容器 class 只有定位/边框/阴影，**没有任何字号类**。
2. `body` 没有全局 `font-size`，于是继承浏览器默认 **16px**；它不在 `.studio-root` 里，拿不到 14px，更拿不到父级 `text-caption`。
3. P5 的 codemod 只重写了**显式**的 `text-[Npx]` / `text-xs` / `text-sm`（256 处 / 71 文件），这些靠「继承」拿字号的菜单项没有被覆盖；`BottomPromptBar.tsx` 里模型/尺寸/质量/数量的选项 `<div>`、`更多` 面板的 `<span className="text-slate-500">` 都是裸文本。
4. P5 删掉了 `studio.css` 11 条字号硬覆盖，主界面由 6 档令牌接管，但**浮层不在 `.studio-root` 作用域内**，等于漏了一层。
5. P5 验收漏测：当时的 Playwright 复检只覆盖菜单键盘（↑↓/Esc）、Modal 焦点陷阱、字体 `loaded`、骨架动画、深浅主题；字号 A/B 量的是主界面，**没有点开浮岛里这 5 个下拉**。

### 7.4 修法方向（只记录，本轮不实施）

1. **全局兜底**：给 portal 浮层一个统一基准字号，例如 `body` 或 `[data-overlay]` 上设 `font-size: var(--type-body-sm)`，或直接在 `Menu` 容器加语义类，避免以后新增浮层再次继承 16px。
2. **局部对齐**：给 `BottomPromptBar` 的 5 个下拉选项与「更多」面板标签补 `text-caption`（12px，与触发胶囊一致）/ `text-body-sm`（13px，可读性更好，二选一，需你定基准），标题可用 `text-body-sm font-semibold`。
3. **不要只改「更多」一个面板**：所有用 `src/ui/Menu` 的浮层都可能中招，应按「全局兜底 + 局部对齐」两层修。
4. **回归清单**：浮岛 5 个下拉 + 停靠模式 + 深浅主题 + 960 窄窗 + 125%/150% DPI + 键盘操作不回退（UI-32 的 ↑↓/Esc/焦点归还仍需通过）。
