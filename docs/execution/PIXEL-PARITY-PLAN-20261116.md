## 七、推进节奏（2026-11-16 修订）

### 7.1 窗口：一个执行 + 一个审查，全程不换

| 窗口 | 数量 | 职责 | 不做什么 |
|---|---|---|---|
| 执行窗口 | 1 个，贯穿 S0–S4 | 写代码、跑门禁、构建安装 | 不自审、不写方案 |
| 审查窗口 | **1 个，贯穿全程** | 方案预审 + 各阶段复审 | 不改代码、不重开已定口径 |

审查窗口常驻的好处：它记得上一阶段的阻塞项，不用每次重讲背景，token 最省。

### 7.2 审查输入只给三样

1. 本阶段 diff（`git show --stat` + 关键文件路径）
2. 门禁结果（build / test / e2e 的 exit code 与用例数）
3. 已知限制清单

**不给**：全仓代码、聊天记录、方案全文（它已经读过一次）。

### 7.3 阶段合并，减少往返

原 S0–S4 合并为三次审查：

| 批次 | 包含 | 审查点 |
|---|---|---|
| B1 | S0 侧栏 + S1 技能库 | 入口正确 + 技能卡三行完整 |
| B2 | S2 设置 | 820×660、五栏、广告按实写、未保存拦截 |
| B3 | S3 工作流 + S4 收口 | 真实运行 + 全量门禁 + 安装 |

每批最多两轮复审，每轮阻塞 ≤3。

### 7.4 先骨架后接线（walking skeleton）

1. 先把三页的**复制版**跑起来（数据可以是空的），一次性做视觉验收；
2. 再逐页接真实数据与运行；
3. 避免“每页改一点、每页都不完整”。

### 7.5 验收先行

每个批次动手前，先把验收命令写死在方案里：

```
npm run build
npm test
npx playwright test e2e/<相关>.spec.ts
```

没有可执行验收的批次不开工。

### 7.6 省 token 的三条硬做法

1. **能用脚本就不生成文件**：复制、改导入、批量重命名用 shell，不让模型重写正文；
2. **审查只看 diff**，不看全文；
3. **执行窗口长跑**，阶段之间不向总控汇报，只有三类阻塞停：丢数据、泄密钥、构建/安装不可用。

### 7.7 回滚点

每个批次结束一个 commit，出问题 `git revert <sha>` 即可，不回退整批。
