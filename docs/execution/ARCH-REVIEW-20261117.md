# 架构与可维护性复审（2026-11-17）

- 角色：只读审查，不改代码
- 范围：`src/` 全量，重点看数据模型、持久化、耦合、巨型文件、测试结构
- 结论：**没有新的发布阻塞项**；但结构债比上次评估更清楚，建议 1.8 专门处理

## 评分（1–10）

| 维度 | 分数 | 依据 |
|---|---|---|
| 模块边界 | 5.0 | 有 `studio/adapters`，但 62 个文件仍直接依赖 store |
| 数据模型 | 4.5 | 技能两套、项目两套、同名类型重复定义 |
| 持久化 | 4.5 | IndexedDB + 7 个 localStorage 键，无统一 schema/迁移 |
| 可读性 | 5.0 | 17 个文件 >800 行，最大 5907 行 |
| 可测试性 | 6.0 | 1137 单测扎实，但新三页缺组件测试，E2E 有 12 条过时 |
| 可运维性 | 4.0 | 73 处 console.error，无诊断导出、无错误上报 |
| **综合** | **5.0** | 能交付，长期演进成本偏高 |

## 主要发现

### F-01 单一事实源仍未建立（高）
- `WorkflowProject` 有 **2 个定义**；`PromptSkill` 有 **2 个定义**；
- 技能仍是两套：能力技能（带输入槽）与提示词技能（纯文本），这次只在 UI 层合并；
- 项目也是两套：画布项目与工作流项目。
- 风险：字段漂移、导入导出对不上、以后加字段只改一边。

### F-02 持久化碎片化（高）
- IndexedDB 存任务/工作区；localStorage 存 7 个键（技能、配置桥、启动页、导出格式等）；工作流项目另有一个键。
- **没有 schema 版本与迁移**；备份/导入是否覆盖全部键未验证（P0-5）。
- 风险：升级或清缓存即丢数据，且用户无从恢复。

### F-03 组件直连 store（中高）
- 62 个文件 `from '.../store'`；adapter 层只覆盖三个模块，内部也直连 store。
- 改一个 state 形状，影响面无法静态评估。

### F-04 巨型文件（中高）
- `store.ts` 5907、`ComfyWorkflowView` 2528、`SettingsModal` 2275、`InputBar` 1895。
- 原型复制件与补丁代码混在同一文件，读一次要跨 2000 行。

### F-05 补丁策略无自动校验（中）
- vendor 只保证“原件不被改”；`src` 里的复制件与原件差 346/199 行，靠文档登记。
- 没有脚本校验“src = vendor + 已登记补丁”，补丁会漂移。

### F-06 错误处理与诊断（中）
- 73 处 `console.error`，失败只进控制台；用户侧没有“导出诊断信息”。
- 发布后支持成本高。

### F-07 测试结构失衡（中）
- 1137 单测集中在 store/lib；新三页没有组件级测试；
- 12 条 E2E 停留在旧界面 → 回归信号失真（本轮已暴露）。

### F-08 性能无预算（中）
- 画布拖拽问题刚修，但没有性能基准与门禁；下次改动可能再次退化。

### F-09 无灰度/开关（低中）
- 原型件直接替换入口，出问题只能整包回退；没有 feature flag。

## 建议（按性价比排序，不在本轮做）

| 优先级 | 动作 | 收益 |
|---|---|---|
| P1 | 数据层收敛：技能统一、项目统一、类型去重 | 消除字段漂移与导入导出错位 |
| P1 | 持久化加 schema 版本 + 迁移 + 备份覆盖全部键 | 升级/换机不丢数据 |
| P2 | 补丁校验脚本：src 必须等于 vendor + 登记补丁 | 防止复制件悄悄漂移 |
| P2 | 诊断信息导出（版本/引擎/最近错误） | 发布后支持成本大降 |
| P2 | 巨型文件按域拆分（store slices、canvas 四组、settings tabs） | 单次改动认知负荷 |
| P3 | 性能基准进 CI（拖拽/首屏） | 防止性能回退 |
| P3 | feature flag / 灰度 | 可局部回滚 |

## 明确不建议现在做的

- 拆 `store.ts`：风险高于收益，等数据层收敛后再动；
- 换状态库：没有收益证据；
- 大规模重写原型复制件：会再次引入“重写导致偏差”。

## 对本次发布的影响

以上均为**结构债**，不构成本次发布的阻塞项。
发布门槛仍以 `RELEASE-READINESS-20261117.md` 的 22 项为准。

## 第三方二次复核（2026-11-17）

- 方法：源码量化 + 持久化链路核对 + 安装版只读 MCP + headless UI 实量；不改业务代码。
- 综合工程健康：**4.8 / 10**。
- 结论：**不建议重写，也不建议继续在现有多套模型上叠功能；先做数据边界、领域语义和回归信号收口。**

### 对上一版事实的校正

- 当前前端：260 个产品 TS/TSX 文件、55,437 行；102 个测试文件、21,877 行。
- 当前超大文件：17 个超过 800 行；`store.ts` 5947 行、`ComfyWorkflowView` 2523 行、`SettingsModal` 2315 行、`InputBar` 1895 行。
- 前端直接依赖 store 的文件：**55 个**（上一版写 62，属旧数据）。
- `WorkflowProject`、`PromptSkill` 当前各只有 1 个同名定义；真正仍重复的是 `Artboard`、`WorkflowPreset`、`SkillItem`、`SkillVariable` 等多视图类型。上一版“同名类型”的结论方向成立，但具体点名不准确。
- 持久化不是简单“7 个 localStorage 键”：实际有 SQLite `kv`、任务/图片表、WebView localStorage 业务键、两个独立 IndexedDB 入口，边界更复杂。

### 本轮新增的硬问题

1. **P0 备份缺口**
   - 工作流项目配置在 `panpan-project-workflows-v1`（原生 localStorage）。
   - 工作流结果图在 IndexedDB `panpan-workflow-results`。
   - ZIP 的 `ExportData`、导出 manifest 和恢复链路均未包含这两项。
   - 结论：普通任务备份成功，不等于完整用户数据备份成功。

2. **领域命名过载**
   - 工作区“项目”是画布容器（`Project/ProjectCanvas`）。
   - 工作流“项目”是可复用流程配置和运行结果（`ProjectWorkflow/WorkflowProject`）。
   - 原型适配层还有 `ProjectFolder/ProjectScheme`。
   - 结论：应统一语义与关系，不应为了“统一”把不同业务对象硬合成一张表。

3. **技能多表示**
   - 持久化有 `Skill` 与 `PromptSkill` 两套数组。
   - UI 再归一化成 `SkillItem`。
   - 旧提示词迁移会复制成 `prompt:` 前缀的 `Skill`，但源提示词库仍保留，形成两套 CRUD 分支与重复风险。
   - 结论：应统一“用户技能注册表 + discriminated union”，保留能力槽与纯提示词两种行为，不强行抹平差异。

4. **回归信号失真**
   - 1140 条单测证明了很多细节，但全量 E2E 仍曾有 15 条失败。
   - 当前 `left-rails` 只检查宽度与折叠，不检查标题、图标、内边距和行对齐。
   - 项目没有 ESLint 配置。

### 最小代价优化顺序

| 顺序 | 动作 | 明确不做 |
|---:|---|---|
| 1 | 建立用户数据清单与统一备份边界：工作区、任务、图片、技能、工作流配置、工作流结果 | 不先重写 store，不换数据库 |
| 2 | 技能统一为一个注册表/存储入口，用 `kind` 区分能力技能与提示词技能，各自保留 payload | 不强行把带槽技能和纯文本技能合成同一行为 |
| 3 | 理清“工作区项目”和“保存的工作流”语义；必要时改名或显式关联 | 不盲目合并成一张项目表 |
| 4 | 抽一个轻量领域服务层给技能、工作流、备份和 MCP 共用 | 不为每个组件再造 adapter |
| 5 | 三处左栏共用同一外壳规格，内容区按槽位传入 | 不做一个万能组件覆盖所有页面 |
| 6 | 补 MCP 只读接口：技能、工作流、脱敏诊断、备份完整性 | 不补成全量 CRUD，不增加第二套业务逻辑 |
| 7 | 更新全量 E2E、补 lint、补备份往返测试 | 不用单测数量代替真实旅程 |

### 不建议现在做

- 全量重写 `store.ts`。
- 更换状态库或数据库。
- 为“架构漂亮”引入复杂 DDD/事件总线/微服务式分层。
- 把 MCP 做成完整管理后台 API。
- 在没有统一备份和迁移前清理真实技能数据。

### 为什么“局部重构”是当前最优可行解

约束前提：

1. 现有安装版和真实用户数据必须兼容；
2. 不停止技能迭代；
3. 不推倒现有生成、任务、安全能力；
4. 不新增大量抽象层。

| 方案 | 优点 | 代价/风险 | 结论 |
|---|---|---|---|
| 不做结构调整，继续叠功能 | 短期最快 | 每个技能字段继续在多模型、多存储、多入口同步；备份和回归风险持续放大 | 不可取 |
| 全量重写 | 理论上模型最干净 | 数据迁移、功能回归、测试重建、发布回滚风险都最大；会浪费现有安全与任务能力 | 不值得 |
| 在现有模型上再加一层万能适配 | 初期改动小 | 只是增加第四种表示和第五个写入口，不解决事实源分裂 | 不可取 |
| 只重构高代价边界 | 可保留现有功能与数据；把未来改动集中到少数入口；可分阶段回滚 | 需要兼容迁移和跨模块验收，但范围可控 | **当前最优可行解** |

必要性证据：

- 工作流备份缺失已经证明：分散持久化不是“代码不优美”，而是已经会产生真实数据风险。
- 技能已有 3 种表示、2 个持久化入口；继续扩展技能类型时，修改点会按表示数量和入口数量放大。
- 55 个前端文件直接依赖巨型 store，但现阶段先大拆 store 风险高于收益；应先减少身份模型和持久化分叉。
- 全量 E2E 与界面已经脱节，说明单靠“多写单测”不能证明跨入口闭环。

因此，重构必要性成立，但必要性只指向 **数据边界、技能身份、项目语义、共享 UI 外壳和回归信号**，不指向全项目重写。
