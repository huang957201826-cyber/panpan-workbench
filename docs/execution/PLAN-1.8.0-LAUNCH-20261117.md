## 5. 核心架构决定

### AD-01：用户数据只有一个备份清单

建立版本化备份 manifest，至少覆盖：

- 工作区项目、画布、图片节点；
- 任务、原图、缩略图；
- Agent 对话及其关联任务；
- 收藏夹和默认收藏夹 ID；
- 能力技能、提示词技能、内置技能覆盖层；
- 保存的工作流、参数和运行记录；
- 工作流输入图和结果图；
- 配置中允许备份的非敏感字段。

API Key、MCP token、签名私钥等敏感值永远不进入备份。

### AD-02：技能使用统一注册表 + 判别联合

技能公共字段统一为身份、名称、描述、分类、收藏、封面、版本和时间。类型差异通过 `kind` 保留：

- `capability`：槽位、图片约束、执行适配；
- `prompt`：提示词、变量、推荐参数；
- 未来新类型：增加一个类型模块和必要的 `normalize / validate / compose` 逻辑；`capability` 继续使用现有执行适配，`prompt` 保持显式合成逻辑，不强行实现通用 `execute` 接口。

禁止通过名称去重；身份只认 ID。历史技能迁移保留原 ID 或使用确定前缀，重复执行必须幂等。测试遗留的 `TestSkill1800` 不在产品迁移中自动删除，只在受控 U2 中按精确 ID 处理。

### AD-03：工作区项目与保存的工作流分离

- 工作区项目继续表示画布容器。
- 当前“工作流项目”改为“保存的工作流”语义。
- 若需要关联工作区项目，使用显式 `workspaceProjectId`；没有关系就允许为空，不使用 `'workflow'` 这类占位业务 ID。
- 原型层 `ProjectFolder / ProjectScheme` 只作为 UI 适配结构，不成为持久化事实源。

### AD-04：左栏共享外壳，不共享数据逻辑

以技能库左栏为视觉基准，抽出轻量 Sidebar shell：

- 统一宽度、背景、边框、标题区、边距、条目高度、圆角、字重和折叠按钮；
- 统一图标尺寸和操作位置；
- 项目、流程、技能分类仍由各自内容组件渲染；
- 不创建覆盖所有业务的万能侧栏。

### AD-05：MCP 只建立在统一领域服务上

新增只读工具：

- `skill.list`
- `workflow.list`
- `workflow.get`
- `diagnostics.get`
- `backup.verify`

工具不直接读取 React store 或 localStorage，不复制业务计算，不新增写入工具，也不为前端与 Rust 另建通用领域框架；只复用稳定的只读存储查询接口。原 `task.create`、`image.attach` 保持现有确认和安全边界。

### AD-06：设置保存保持原样

普通偏好继续自动保存；API 配置继续使用独立草稿和显式“保存此配置”。本批不删除按钮、不修改左侧说明。

### AD-07：本地更新签名与公开资产边界

- 不使用 Authenticode 代码签名证书。
- Tauri updater 的私钥和密码只保存在维护者本机，不提交、不上传、不进入 ZIP 备份或日志。
- 公开 Release 只包含安装包、公开验证用的 `.sig`、`latest.json`、SHA256 和发布说明。
- 若仓库或自动化需要占位，只提交空值模板；不得提交真实私钥、密码、GitHub Secret 或本机绝对路径。
- Tag 触发的桌面发布 workflow 改为验证/构建门禁，不依赖私钥 Secret、不自动上传桌面 Release。最终安装包和 `.sig` 由本机签名构建后，经用户明确授权再人工上传。
- 上传前必须校验 `.sig` 对应最终安装包、安装包 SHA256、`latest.json` 版本和下载 URL，四者一致。

### AD-08：恢复必须有统一提交点与明确冲突模式

恢复采用可恢复的 `RestorePlan`：

1. **解析**：读取 ZIP、manifest 和文件清单，不写业务数据。
2. **校验**：校验版本、哈希、文件完整性、ID 和引用；任何错误在预览阶段失败。
3. **冲突预览**：统计新增、同 ID、缺失图片和将被替换的数据。
4. **安全快照**：快照失败、空间不足或排空超时必须中止，且不得进入 staging。
5. **Staging**：工作流结果图先写入 IDB 不可变暂存 ID；SQLite 业务记录写入临时表或暂存数据；现有业务数据保持不变。
6. **Commit**：工作流元数据在 S1 前置迁移到 SQLite 后，只以 SQLite 单事务作为可见提交点，一次写入任务、工作区、技能、工作流和指向不可变暂存图片 ID 的引用。IDB 图片本身不参与 SQLite 事务。
7. **Hydration**：提交成功后刷新 store 内存、tauriStorage 缓存和 IDB 图片缓存，确认新快照已可见。
8. **Cleanup**：提交后清理旧记录和未引用暂存图片；清理失败只留下无害孤儿，不改变已提交结果。
9. **Recovery**：启动时在 store hydration 前按 journal 回收失败 staging，不能出现半恢复。

恢复模式固定为：

- **合并恢复（默认）**：保留当前数据，只新增备份中不存在的 ID；同 ID 一律跳过，不覆盖。
- **替换恢复**：用户二次确认后，以备份替换所选业务类别；同 ID 使用备份记录。
- Agent 对话与关联 Agent 任务按组合类别处理：合并时若对话 ID 已存在，跳过该对话及其关联任务，不产生半套记录。
- 收藏夹合并时保留现有同 ID；默认收藏夹 ID 保留当前值，当前为空时才使用备份值；替换时整体使用备份收藏夹和默认 ID。
- 两种模式都先自动生成当前数据安全快照。
- 恢复写锁固定为：
  1. `acquire` 恢复锁；
  2. 阻止新的生成、删除、清空、导入和恢复；
  3. bump 任务/存储写 epoch，取消在途任务并隔离迟到回调；
  4. 等待 `waitForTaskWrites=0`；
  5. flush `tauriStorage`，成功后清空恢复前的 dirty key；
  6. 生成安全快照；
  7. staging；
  8. SQLite commit；
  9. 刷新内存、kv 和 IDB 缓存；
  10. cleanup 后 unlock。
- 排空超时、写队列 flush 失败、快照失败、空间不足或 staging 失败都必须在 commit 前中止并解锁，不得修改现有业务数据。
- commit 后旧 epoch 的迟到回调必须被拒绝，不能覆盖恢复后的数据。

## 5.1 架构改动落位

架构调整不是一个可以拖到最后的独立阶段，而是按风险和依赖拆入执行阶段：

| 架构调整 | 所在阶段 | 级别 | 内容 |
|---|---|---:|---|
| 用户数据、工作流元数据与备份边界统一 | S1 | A | 工作流 metadata 先迁入 SQLite；建立统一备份 manifest、结果图导入导出、恢复锁和清空口径 |
| 技能领域模型统一 | S2 | A/B | 单注册表、判别联合、类型处理器、统一 CRUD 和迁移 |
| 工作流实体与语义收口 | S3 | B | 工作区项目与保存的工作流改名分离；旧 key 兼容读取与最终清理 |
| 共享 UI 外壳 | S4 | C | 三处左栏共享 Sidebar shell，数据内容仍分离 |
| MCP 服务边界 | S5 | B | 只读工具复用统一技能、工作流、备份和诊断服务 |
| store 薄适配 | S1-S3 | B | 保留现有 store，只在新领域服务外围增加薄适配，不整体拆分 |

依赖顺序固定为 `S1 → S2 → S3 → S4 → S5`。工作流元数据迁入 SQLite 属于 S1 的前置步骤，必须先于恢复实现；S3 不再承担存储迁移。

## 6. 数据模型与迁移

### 6.1 数据清单

| 数据 | 当前存储 | 目标 |
|---|---|---|
| 任务、图片、缩略图、Agent 数据 | SQLite | 保持，进入统一备份 |
| 设置、工作区、技能 | Tauri 存储适配器 → SQLite kv | 技能收口到版本化注册表 |
| 保存的工作流 | WebView localStorage | S1 前置迁移到 SQLite 统一业务存储；旧 key 只读兼容，S3 最终清理 |
| 工作流结果图 | IndexedDB dataUrl | 保持 IDB，但进入 ZIP 文件导出/恢复 |
| UI 临时偏好 | localStorage | 不视为业务数据；明确无需备份 |

### 6.2 迁移要求

- 每个迁移有 schema 版本和幂等保护。
- 先读取并校验旧数据，再写入新结构；全部成功后才标记迁移完成。
- 迁移失败保留旧数据和错误信息，不删除源数据。
- 1.7.0 旧备份仍可导入；1.8.0 新备份可由当前版本恢复。
- 工作流 IDB 图片缺失时，记录保留并显示“图片缺失”，不允许整批导入失败。
- 清空操作只删除用户明确选择的数据；界面必须准确说明范围。

### 6.3 回滚

- 代码回滚点：本批开始前最新本地提交。
- 数据回滚：迁移前完整 ZIP + 数据目录副本。
- 安装回滚：1.7.0 安装包与数据备份。
- 若新结构写入失败，应用继续使用旧结构启动。

### 7.3 MCP 新工具契约

所有新工具只读、分页上限 200，错误返回稳定代码 `invalid_argument | not_found | unavailable | write_disabled | rate_limited`，不得返回绝对路径、日志原文、API Key、MCP token 或设置快照。

| 工具 | 请求 | 成功响应 |
|---|---|---|
| `skill.list` | `limit?`, `offset?`, `kind?` | `total`、`offset`、`limit`、`items[]`：`id/kind/name/description/category/tags/favorite/source/version/updatedAt/slotCount/promptLength` |
| `workflow.list` | `limit?`, `offset?`, `workspaceProjectId?` | `total`、`offset`、`limit`、`items[]`：`id/name/presetId/workspaceProjectId/resultCount/hasMissingImages/updatedAt` |
| `workflow.get` | `id` | `id/name/presetId/workspaceProjectId/values/results[]`；结果只含记录元数据和 `imageId/inputImageId` |
| `diagnostics.get` | 无 | `appVersion/platform/databaseOk/storageOk/engineStatus`，以及 `counts`、`recentErrors[]`；错误只含 `code/at/summary`，不含堆栈、路径或原文 |
| `backup.verify` | 无 | `ok`、`manifestVersion`、`categories[]`：名称、是否存在、计数、错误代码；不返回文件路径 |

`diagnostics.get` 的 `summary` 还要统一清除 Windows 盘符路径、UNC 路径、`file://`、Bearer、API Key、MCP token、查询参数中的敏感值。HTTP 继续执行 Host、Origin、Bearer；stdio 只暴露只读工具。

## 8. 失败模式与降级

- 备份导出失败：不显示成功，不删除任何数据。
- 备份导入部分失败：事务式回滚或明确列出未恢复项。
- 工作流图片缺失：保留记录和错误标记，可删除或重新运行。
- 技能迁移失败：旧 store 只读，提供重试和诊断。
- 拖动过程异常：松手恢复原位置或落点，不丢失节点参数。
- MCP 读取失败：返回结构化错误，不泄漏路径和密钥。
- 更新校验失败：保留当前版本，不替换安装包。
- 数据目录不可写：应用继续可启动但明确提示，禁止静默丢写入。

## 12. 替代方案与不选理由

- **继续叠功能**：不解决事实源分裂，未来技能扩展继续放大修改点。
- **全量重写**：迁移、回归、安装和回滚风险过高，不符合最小代价。
- **再加万能适配器**：会增加更多表示和入口，不解决根本问题。
- **先把 store.ts 拆完**：风险高于当前收益；先收敛数据和领域边界。
- **设置全部改自动保存**：用户已明确维持原样，且会扩大校验和迁移范围。

## 13. 主要风险

| 风险 | 缓解 |
|---|---|
| 技能迁移损坏旧数据 | 副本 dry-run、幂等迁移、保留旧 key、导出快照 |
| 工作流图片体积过大 | ZIP 分卷、图片文件引用、缺失降级 |
| UI 统一影响业务内容 | 只共享外壳和令牌，不共享列表逻辑 |
| 发布范围膨胀 | known-limits 冻结，新功能不进入 1.8.0 |
| 签名私钥丢失 | 离线备份与责任人记录；发布前验证签名 |
| 私钥误上传 | 提交前秘密扫描；Release 资产白名单；仓库只允许空模板 |
| 文档再次漂移 | 版本、README、RELEASE、latest.json 同门禁校验 |
