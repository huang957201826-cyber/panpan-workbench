# 执行规则（最高优先级）

- 日期：2026-11-10（v3）
- 状态：生效，覆盖此前任何“子方案/逐项复审”的做法
- 适用：总控窗口、开发窗口、审查窗口、后续所有会话
- 用户命令：**只做一份大方案；不要子方案；抓大放小；不要回到上上版意见；把命令落到 MD，防止上下文压缩后丢失。**

## 1. 角色

| 角色 | 职责 | 禁止 |
|---|---|---|
| 总控（当前窗口） | 意见收口、总方案、阶段边界、派发、收证据、安装/U2、汇报 | 不写业务代码 |
| 开发窗口 | 唯一写代码/配置/脚本；长阶段实现、测试、构建候选 | 不写子方案、不逐项问、不扩范围 |
| 审查窗口 | 只读；方案预审查 + 阶段复审 | 不改代码、不重开已冻结决策、不逐项挑刺 |

## 2. 方案规则（只允许一份）

1. 每个大批次只允许一份总方案，文件名随批次变化（如 `PLAN-B02.md`）。
2. **禁止再写 `B02-1B-1`、`B02-2A`、`B02-3-1` 之类子方案**。
3. 总方案一次预审查通过后冻结；后续开发直接按本批次 `CHECKLIST` 做，不再逐阶段做方案复审。
4. 只有“范围/授权文件/验收口径”真的变化时，才允许在总方案里做一条短修订，并只复审该修订；不重写整份方案。
5. 已冻结的决定不得因为新会话/上下文压缩而重新讨论；以总方案、本批次 `CHECKLIST`、`CHECKPOINT.md` 为准。

### 2.1 批次生命周期（强制顺序）

一个批次从收到意见到收口，固定六步，缺一步不得进入下一步：

| 步骤 | 产出 | 负责 | 通过条件 |
|---|---|---|---|
| 1. 意见收口 | `LEDGER.md` / 清单条目 | 总控 | 用户意见全部编号，无遗漏；未收口不写方案 |
| 2. 汇总成文档 | 一份总方案 + 一份逐项清单 | 总控/开发 | 范围、验收口径、回滚点齐全 |
| 3. 方案预审查（分级） | 影响分级 + `ARCH_REVIEW` / `PLAN_REVIEW` | 审查窗口 | A/B 级先过架构预审，再过执行预审；C/D 级只走执行预审 |
| 4. 正式放行 | 冻结哈希 + 阶段顺序 | 总控 | 预审查 `APPROVE`；未冻结不开发 |
| 5. 逐阶段执行 | 阶段 `REPORT` + `GATES` | 开发 | 阶段验收 + 阶段复审 `APPROVE` |
| 6. 收口 | `CHECKPOINT` + 最终报告 | 总控 | 全部阶段完成，回滚点明确 |

- 方案预审查分两级：A/B 级改动先做架构预审（`ARCH_REVIEW`），再做执行预审（`PLAN_REVIEW`）；C/D 级只做执行预审。
- 影响分级：A 数据/存储/安全/安装/跨平台；B 共享状态/动作层/双视图/核心交互；C 局部 UI/文案；D 文档/内容。
- 架构预审审“后期改代价高”的决策：模块边界、状态归属、接口契约、数据迁移、并发/竞态、失败模式、性能、安全、可测试性、双视图一致性和回滚。
- 执行预审审三件事：会不会丢数据/泄密钥/导致构建安装不可用；范围有没有明显缺口或自相矛盾；验收口径是否可执行、可回滚。
- 预审查最多两轮；第二轮仍 `REJECT`，降范围、拆批次或换方案，不硬推。
- 阶段复审在每个大阶段末做一次；未通过不得进下一阶段。
- 预审查和阶段复审都只审“是否越过冻结范围”，不重开已冻结的业务口径。

### 2.1.1 当前 Codex 单窗口协作模式（2026-11-17 用户确认）

适用于用户当前使用的 Codex 环境，覆盖“总控与开发必须分窗口”的默认假设：

1. 当前窗口同时承担**项目总控、主开发、验收证据整理和整改**，不额外要求开发窗口。
2. Codex 当前窗口不能自动创建、控制或等待另一个审查窗口。
3. 独立审查由用户在 Codex 新任务中完成；当前窗口只准备审查输入和接收结论，不得自审代替。
4. 方案预审必须先完成。没有独立窗口的 `ARCH_REVIEW=APPROVE` 和 `PLAN_REVIEW=APPROVE`，不冻结方案、不写业务代码。
5. 每个大阶段完成后，当前窗口先产出：
   - `REPORT-<批次>-<阶段>.md`
   - `GATES-<批次>-<阶段>.json`
   - 相关 diff / 提交号 / 测试输出 / 截图或 trace
   - 一份可供引用的审查输入 MD
6. 用户面不要直接粘贴整份审查 MD。当前窗口应只输出**一段可直接复制的审查提示**，其中引用仓库内审查文档和证据路径；用户复制到独立审查任务即可。
7. 独立审查返回结论后，用户把结论完整贴回当前窗口。只有 `CODE_REVIEW=APPROVE` 才能进入下一阶段。
8. 审查最多两轮：第一轮只列最多 3 个阻塞项；第二轮只修阻塞项并做定向验证，不扩大范围。
9. 阻塞仍只限三类：丢数据/损坏数据、泄漏密钥或安全边界、构建/安装/启动/更新/MCP 不可用。其他问题写 `known-limits`。
10. 当前窗口负责执行修正，但仍不得自行宣布独立审查通过。

#### 用户面审查提示格式

默认只输出类似下面的一段话，并把尖括号内容替换为实际路径：

> 请作为本项目独立只读审查窗口，不要修改任何文件。请先阅读 `<审查输入 MD>`，再读取其中引用的总方案、清单、阶段报告、门禁结果、diff/证据，以及必要的源代码。只按“丢数据、密钥泄漏、构建安装不可用”三类判断阻塞，抓大放小，不扩张需求、不重开已冻结口径。请输出 `CODE_REVIEW=APPROVE|REJECT`、最多 3 个阻塞项和最多 3 个允许带入 U2 的条件；不要开始实现。

方案预审时把最后一句改为输出 `ARCH_REVIEW` 和 `PLAN_REVIEW`，并同样限制最多 3 个阻塞项。

### 2.1.2 Token 受限合并执行模式（2026-11-18 用户确认）

本规则适用于当前 `1.8.0-LAUNCH` 剩余阶段，覆盖 §2.1.1 中“每个原始 S 阶段单独审查”的执行口径，但不缩减冻结方案的技术范围：

1. `S1` 仍独立完成当前复审；这是数据恢复与丢数据风险边界，不和后续阶段混合。
2. `S1` 通过后，剩余阶段合并为三个施工与审查批次：
   - 批次 A：`S2 + S3`（技能注册表、工作流语义）；
   - 批次 B：`S4 + S5`（三栏 UI、拖动性能、MCP 只读诊断）；
   - 批次 C：`S6 + S7`（测试/文档/发布工程、最终构建安装与 U2）。
3. 每个合并批次只做一次连续实现、一次批次报告、一次批次门禁、一次独立代码复审。
4. 不再为每个小问题、原始 S 阶段或复审整改重复生成完整报告、哈希包和源码快照。审查输入默认只给：
   - 一份简短审查 MD；
   - 当前源码路径；
   - 相对基线的 diff 或提交号；
   - 批次末测试/构建/截图/trace 证据路径。
   只有独立审查明确要求时，才补完整审查包。
5. 开发过程中只跑受影响测试；`gate:dev`、Rust 全量测试、全量 E2E 放到合并批次末跑一次。最终安装只在批次 C/S7 做一次。
6. 每批仍最多两轮复审，阻塞仍只限丢数据、密钥泄漏、构建/安装/启动/MCP 不可用三类。非阻塞项直接记 `known-limits`，不扩大整改。
7. 发布授权规则不变：只本地提交和构建，push/tag/公开 Release 仍须用户明确授权。

### 2.2 自动化门禁

- 本地基础门禁：`npm run gate:dev`（构建 + 单测 + 静态检查 + dist 扫描）。
- 行为验收：`npm run e2e`（Playwright + Edge + mock API）。
- 完整门禁：`npm run gate:all`（基础门禁 + Rust + E2E）。
- 远端第二意见：`b02` push 后 GitHub Actions；CI 失败先修，不把红当绿。
- 阶段专用验收脚本放 `scripts/verify/`，输出 JSON/截图到 `docs/execution/evidence/`；没有脚本的验收，用 `gate:dev`/`e2e` 的 exit code + 证据路径代替。

### 2.2.1 发布闸门（最高优先级）

- **未经用户明确口头同意，禁止把代码上传到任何公开仓库、公开盘或公共 Release。**
- “继续开发”“可以安装”“你自己评判”“修完这批”都不等于发布授权。
- 发布授权必须是用户明确说出“可以发到公共盘/可以上传仓库/可以发布”这类意思；一次授权只对应一次发布，不默认延续到下一版。
- 本地提交、构建、安装、备份不受此闸门限制；受限的是 push 到公开远端、上传 Release 资产、部署网页版。
- 每次准备发布前，先在汇报里写“等待发布授权”；没有这句授权，停在本机。

### 2.3 分级方案预审（A/B 级必做）

#### 3.1 影响分级

- **A 级**：数据/存储/安全/安装/跨平台；必须架构预审。
- **B 级**：共享状态/动作层/双视图/核心交互；必须架构预审。
- **C 级**：局部 UI/文案/样式；只做执行预审。
- **D 级**：文档/内容；只审范围。
- 分级表写入总方案；未分级不进入预审。

#### 3.2 架构预审（只做 A/B）

审查窗口先读相关代码路径，再审这些“后期改代价高”的决策：

- 模块边界与依赖方向：是否继续吹大 `store.ts`、是否循环依赖、是否引入第二套动作/选中态；
- 状态归属：任务选中、素材选中、技能 chip、下载状态、布局状态是否单一事实来源；
- 接口契约：类型、命令、事件、存储 key、跨层调用；
- 数据兼容：旧数据、旧草稿、旧 ZIP 备份、版本迁移；
- 并发/异步/竞态：保存、生成、切换画布、删除、下载同时发生时谁赢；
- 失败模式：失败是否可见、可重试、可回滚，不能静默失败；
- 性能/资源：大图、长列表、3000 节点、分块写入；
- 安全/权限：Key、MCP、本地文件、路径校验；
- 可测试性/可维护性：能否用一条 E2E 锁住，文件是否继续膨胀，证据是否可回放；
- 双视图一致性：动作 × 画布 × 九宫格 × 右侧抽屉的 parity matrix；
- 发布/回滚：安装版、版本号、旧包回滚、数据备份。

#### 3.3 执行预审（全量）

审三件事：

- 会不会丢数据/泄密钥/导致构建安装不可用；
- 范围有没有明显缺口或自相矛盾；
- 验收口径是否可执行、可回滚。

#### 3.4 结论与冻结

- 架构预审输出 `ARCH_REVIEW=APPROVE|REJECT|CONDITIONAL`，架构阻塞最多 3 个，非阻塞风险最多 5 个。
- 执行预审输出 `PLAN_REVIEW=APPROVE|REJECT`，阻塞最多 3 个。
- 通过后冻结 ADR、接口、状态归属、双视图 parity matrix；后续改动只做一次短的 delta 审查，不重开整份方案。

#### 预审准入材料（Definition of Ready）

方案里必须已有：

1. 现状 vs 目标流程；
2. 改动边界（哪些模块/文件/不动）；
3. 数据模型、迁移、兼容、回滚；
4. 接口契约（类型、命令、事件、存储 key）；
5. 双视图一致性矩阵；
6. 失败模式与降级；
7. 测试策略（单测/E2E/安装版/失败注入）；
8. 替代方案与不选它的理由。

缺项退回作者补充，不进入预审。**预审不是帮你想方案，是审方案是否站得住。**

#### 防 churn

- 架构预审是一次设计审查，不是逐行代码审查；逐行实现审查仍在阶段末 `CODE_REVIEW`。
- 最多两轮；第二轮仍 `REJECT`，总控决定降范围、拆批次或换方案，不开第三轮全审。
- 只审“改错会失控”的决策，不挑命名、样式、个人偏好。
- 通过后冻结；改冻结的接口/状态归属只做短 delta 审查。

## 3. 开发规则（长阶段）

1. 开发窗口按总方案里的阶段顺序连续做；一个阶段一次长跑。
2. 不逐项找总控确认；只有业务口径未定、环境硬阻塞、需要改冻结范围时才停。
3. 本批次 `CHECKLIST` 是逐项权威清单；开发结束必须把本阶段归属项标 `[x]` 或 `[-]`，不得留 `[ ]`/`[~]`。
4. 优先复用现有实现/成熟库；不重写 store、不换数据库、不引入新架构。
5. 不做用户没要求的复杂系统；能轻量解决的，不建完整平台。
6. 提交按阶段聚合，不按每个小问题拆 commit。

## 4. 复审规则（抓大放小）

1. **只在每个大阶段末做一次代码复审**；不逐项复审、不做子阶段复审。
2. 每个阶段最多两轮复审：
   - 第一轮列阻塞项；
   - 第二轮只修阻塞项，不再扩展新问题；
   - **第二轮结束后不再开第三轮全审**；只对修复项做定向验证，未闭环项写 known-limits，直接进入 dry-run/U2。
3. **每轮最多列 3 个阻塞项**，按严重度排序。
4. 只有以下三类算阻塞：
   - 会丢数据/损坏数据；
   - 会泄漏 API Key/Token/敏感路径，或破坏安全边界；
   - 会导致构建、安装、启动、MCP 不可用。
5. 以下不阻塞，记入 `knownLimits` 或后续批次：
   - 命名、文案、样式、非关键 UI；
   - 非关键测试覆盖、测试写法；
   - 性能微优化、可访问性细节；
   - 不影响主路径的边界情况。
6. 复审不得重开已冻结的方案/业务口径；只审实现是否符合冻结范围。
7. **先审源码 diff，通过后再构建候选**；避免“审一次、重建一次”。
8. 复审输出只写：`CODE_REVIEW=APPROVE|REJECT`、阻塞项（最多 3）、允许带入 U2 的条件（最多 3）。

### 4.1 三类复审

- 架构预审：A/B 级方案开始时一次，审架构、状态、接口、迁移、并发、失败、性能、安全、可测试性、双视图一致性；输出 `ARCH_REVIEW`。
- 方案执行预审：批次开始时一次，审范围、验收口径、硬伤；输出 `PLAN_REVIEW`。
- 阶段复审：每个执行批次末一次；当前批次合并映射见 §2.1.2；审实现是否符合冻结范围，输出 `CODE_REVIEW`。
- 三者都最多 3 个阻塞项；架构预审最多两轮，方案预审最多两轮，阶段复审最多两轮。

### 4.2 复审输入包

由总控启动审查窗口（或审查子会话），按复审类型给输入包；审查窗口不读全量聊天记录：

- 架构预审：总方案的架构章节 + 相关代码路径 + 双视图 parity matrix + 迁移/回滚/测试策略；不要求全量 diff。
- 方案执行预审：总方案 + 本批次 `CHECKLIST`（含范围、验收口径、回滚点）。
- 阶段复审：本阶段 diff / 提交号 + `gate` JSON / E2E 截图/trace + 已知限制与回滚点。

输出只写：`ARCH_REVIEW`/`PLAN_REVIEW`/`CODE_REVIEW=APPROVE|REJECT|CONDITIONAL`、最多 3 个阻塞项、架构非阻塞风险最多 5 个、允许带入 U2 的条件（最多 3 条）。

### 4.3 失败处理

- 每个执行批次验收必须对关键前提做一次失败注入：故意破坏关键前提，验收必须红；恢复后必须绿。没有失败注入的验收不算通过。
- 同一做法连续失败 2 次，必须换路线：换数据 / 换配置 / 换实现 / 换选题；不得在原地换第三种写法硬试。

## 5. 构建、安装与 U2

1. 代码复审 APPROVE 后才构建候选；候选 SHA256 写入 GATES/REPORT。
2. 安装/U2 由总控执行；开发窗口不安装、不写真实数据。
3. U2 默认使用测试数据副本；真实数据只在数据迁移门禁的“受控首次启动”例外中写入，且必须先双备份、副本 dry-run、记录 pre/post 哈希/任务数。
4. 安装失败按回滚点回退；报告第一个失败门，不硬交付。
5. 不拿单测冒充 U2；真实点击/真实数据副本才算 U2。

### 5.1 阶段完成定义（DoD）

同时满足才算完成，缺一项不得进下一阶段：

- 本阶段清单项全部 `[x]` 或 `[-]`；
- 阶段验收脚本 `exit 0`，并有失败注入记录；
- 证据路径写入 `GATES`/`REPORT`；
- 审查窗口 `CODE_REVIEW=APPROVE`；
- 涉及 A/B 级改动的阶段，ADR / 双视图 parity matrix 已更新；
