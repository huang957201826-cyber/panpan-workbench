## 三、A 代码架构（6.5 / 10）

**做得好**
- 分层清楚：`lib/`（纯逻辑）、`hooks/`、`components/`、`studio/`（新外壳）、`src-tauri/`（Rust 存储与命令）。
- 规模：前端 296 个 TS/TSX 文件、34,979 行；Rust 9,574 行。
- 测试厚：**1021 条前端用例**（84 个文件）+ **105 条 Rust 用例**，`store.test.ts` 单文件 7541 行；`npm test` 全绿。
- 迁移与兼容有意识：`normalize*` 系列处理 IndexedDB/旧数据、`DB_VERSION` 升级路径。
- 无 `TODO`/`FIXME` 残留，无 `any` 泛滥（`tsc -b` 严格模式通过）。

**扣分点**
| 问题 | 证据 | 影响 |
|---|---|---|
| 超大单文件 | `store.ts` **6285 行**（文件上限建议 ≤800）、`InputBar.tsx` 2059、`SettingsModal.tsx` 1940 | 改一处要读半天，回归风险高 |
| 死代码/双实现 | 旧画廊整套（`CanvasWorkbench`/`TaskGrid`/`Header`/`InputBar`/`FavoriteCollections`）仍在，只是没入口；`CardGridView.tsx:17` `Trash2` 未使用 | 打包体积、维护成本、reviewer 困惑 |
| 无 lint / formatter | 仓库无 eslint / prettier / biome 配置，只有 `tsc` | 风格靠约定，外部贡献者 PR 无法自动把关 |
| 无 E2E | devDeps 无 playwright/cypress；UI 回归全靠手点 | 画布交互、拖拽这类最容易坏的地方没有自动化 |
| 单例状态耦合 | 30+ 组件直接 `useStore.getState().xxx()` 命令式调用 | 难以测试、难拆 |
| 产物体积 | `dist/assets` **34 MB**，其中 30 MB 是字体：三份 HarmonyOS Sans **TTF 各 7.9 MB** + 一份 MapleMono woff2 6.1 MB | 安装包 28.8 MB 主要被字体占据；CJK 字体转 woff2 子集可压到 8–10 MB |

**建议**：发版前只做"低风险清理"（删无用 import、把 `docs/execution` 排除），`store.ts` 拆分留给 1.1，避免发布前动地基。

## 四、B 开源协议与合规（7.5 / 10）

**做得好**
- `LICENSE`：MIT，且保留上游 `Copyright (c) 2026 CookSleep` + 补 `panpan`，符合 MIT 义务。
- 依赖许可：扫描 461 个包，**无 GPL/AGPL/SSPL**；唯一例外是 `sharp` 的 Windows 平台二进制（Apache-2.0 AND LGPL-3.0-or-later），它只经 `wrangler`（devDependency）引入，**不随安装包分发**，可接受。
- `src/assets/third-party-notices.txt` 自动生成（Rust 336 + npm 244），应用内"设置 → 关于 → 第三方许可"可查。
- `package.json` 已有 `license: MIT`、`author`、`repository`。
- `.github/ISSUE_TEMPLATE` 三件套齐全。

**扣分点**
| 问题 | 说明 |
|---|---|
| 缺 `CONTRIBUTING.md` / `CODE_OF_CONDUCT.md` | 开源项目的基本门面，issue/PR 引导全靠自觉 |
| `package.json` 缺 `description`；`private: true` | 元数据不完整（`private` 对应用无妨，但会让外部贡献者困惑） |
| `SECURITY.md` 联系方式含糊 | 只写"仓库维护者公开资料中的联系方式"，没有邮箱或 Security Advisory 链接，等于没有报告渠道 |
| **推广链接未披露** | `README.md:36` 与 `sponsor-presets.json` 内含 `aff=rf9W` 返利参数，README 未注明"含推广返利" —— 开源项目里这属于信任问题，建议一句话写清楚 |
| `khroma 2.1.0（未声明）` | 第三方许可清单里标"未声明"，实际是 MIT（`node_modules/khroma/license`），应在生成脚本里补映射，避免清单出现 UNKNOWN |

**结论**：法律链路是安全的（MIT + 无强 copyleft），合规材料"缺件"而不是"违规"。补 3 个文件 + 1 句披露即可。

## 五、C 前端 UI（4.0 / 10）★ 最大短板

已单独出两份文档：`UI-AUDIT-20261107.md`（23 项视觉问题）、`UI-GAP-MATRIX-20261107.md`（需求 × 现状矩阵）。这里只做发布视角的取舍：

**会直接影响"第一印象"的（建议列为发布阻断）**
1. **蓝色光标与点阵是两套特效叠加** —— 截图第一眼就是一块蓝色污渍。
2. **hover 图片节点弹半透明提示词卡 + 浏览器原生白框 tooltip** —— 观感像半成品。
3. **底部输入台被裁切**（"更多…"变"更:"）、菜单向上溢出屏幕、控件 12 个挤一行 —— 第一次用就会点不到。
4. **图片不按真实比例**，1:1 的图塞进 2:1 的框、左右大白边 —— 这被用户直接点名。
5. **九宫格与画布两套操作体系**（7 文字按钮 vs 5 图标），同一功能三种叫法（垫图/参考图/引用）。

**可以做但不必卡发布的**
- 侧栏 44→56px、统一 header 独立行、设计令牌与 primitives、技能库按参考源码重构、设置页风格对齐。

**为什么扣到 4 分**：不是"丑"的问题，是**没有系统**——16 种字号、6 种圆角、3 套图标画法、3 套视觉语言（Studio / 设置页 / 原生控件）。开源项目的 README 头图就是这些截图，UI 就是转化率。
